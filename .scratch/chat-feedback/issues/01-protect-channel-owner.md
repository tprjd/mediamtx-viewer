# 01: Protect a Channel owner from restrictions in their own Chat room

Status: resolved
Category: enhancement
Priority: High
Blocked by: none

## Request

An administrator must not apply a Chat timeout or Chat ban to a Channel owner in that owner's Chat room.

## Evidence

The current domain definition explicitly permits this. The existing timeout and ban authority tests pass with administrator restrictions against Channel owners allowed.
This request supersedes that part of the original Chat policy.

## Proposed acceptance criteria

- Both restriction endpoints reject a target who owns the current Channel.
- Message action menus omit the unavailable restriction actions.
- A Channel owner remains subject to normal moderation in another owner's Chat room.
- Message removal remains a separate permission.
- The domain definition and authorization tests reflect the new policy.

## Accepted decision

On 2026-09-17, the maintainer accepted lifting existing Chat restrictions against a Channel owner in that owner's Chat room.
Record each reversal in a Chat moderation record. Leave removed messages removed.
Restrictions in other owners' Chat rooms remain subject to normal moderation rules.

## Agent Brief

**Category:** enhancement

**Summary:** Protect the current Channel owner from Chat restrictions in their own Chat room and lift existing restrictions there.

**Current behavior:**

Administrators can apply a Chat timeout or Chat ban to a Channel owner in that owner's Chat room.
The restriction blocks messages and removes the owner's moderation authority and Owner badge.
The message menu offers restriction actions against the owner. Existing bans remain active until reversed.
The domain definition and authorization tests explicitly permit this behavior.

**Desired behavior:**

No Chat moderator can restrict the current Channel owner in that owner's Chat room, including the owner acting on their own messages.
Determine protection from the Channel's current owner, not a message's historical display name or badges.
Keep Message removal as a separate permission.

When the new policy takes effect, lift existing active timeouts and bans against owners in their own rooms.
Record each reversal, preserve the original moderation history, and leave removed messages removed.
The owner can send messages and moderate again, subject to the existing account and Channel access rules.
Connected clients must receive the resulting restriction-state change.
Restrictions in other owners' rooms remain unchanged.

**Key interfaces:**

- `applyChatTimeout`, `applyChatBan`, and their shared `applyChatRestriction`: reject protected targets before any restriction or message-removal side effects.
- `getChatMessageActions`: omit timeout and ban actions for protected targets while preserving Message removal permissions.
- `getChatModeratorRole`, `getChatParticipantState`, and `currentChatBadges`: reflect the owner's restored authority, restriction state, and Owner badge.
- `getActiveChatRestriction`, `getChatRestriction`, and `sendChatMessage`: enforce the same policy after existing restrictions are lifted.
- `reverseChatRestriction` and Chat moderation records: use the existing reversal behavior as the reference for history and private state notifications.

**Acceptance criteria:**

- [x] Both restriction endpoints return HTTP 403 for an otherwise valid request targeting the current Channel owner in their own room.
- [x] Rejected requests create no restriction, moderation record, message removal, or delivery event.
- [x] Protection applies when an administrator owns the Channel and when an owner targets their own message.
- [x] Message menus omit both restriction actions for protected targets. Message removal retains its existing authorization rules.
- [x] Owning a different Channel grants no protection in the current Chat room. Existing administrator protections remain unchanged.
- [x] Existing active owner timeouts and bans in their own rooms are lifted when the policy takes effect, without a manual action per restriction.
- [x] Each lifted restriction has one durable reversal record linked to its source restriction. Record the policy change as the cause without falsely attributing it to a human action.
- [x] Repeating the cleanup creates no duplicate reversal records or notifications. Expired restrictions and restrictions in other rooms remain unchanged.
- [x] After cleanup, participant state reports no restriction, and an otherwise eligible owner can send messages and moderate with the Owner badge present.
- [x] Connected clients refresh their private restriction state. Removed messages remain removed, and existing moderation history is preserved.
- [x] The domain definition and authorization tests describe the new policy. Tests cover endpoint rejection, menu permissions, existing-restriction cleanup, repeated cleanup, and moderation in another owner's room.

**Out of scope:**

- Changes to Message removal permissions or the recent-message removal behavior for valid restrictions against other participants.
- Restoration of removed message content.
- Changes to account activation, Viewing access, Streaming access, Channel ownership, or administrator protection in other owners' rooms.
- General moderation UI redesign, history clearing, retention changes, or unrelated Chat feedback.

## Implementation, 2026-09-17

Both restriction endpoints reject the current Channel owner. Message menus use the same protection while keeping Message removal available.
Chat storage open lifts active owner restrictions atomically with a system reversal record and a private notification.
The cleanup also runs when restored storage opens. It preserves removed messages, restrictions in other rooms, and existing moderation history.
The system actor identifies the policy change in the administrator history and passes restore reference validation.
