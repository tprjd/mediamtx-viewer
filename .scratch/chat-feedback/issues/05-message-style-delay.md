# 05: Keep Chat message appearance consistent during submission

Status: resolved
Category: bug
Priority: Normal
Blocked by: none

## Request

After sending, the participant's display name and message first appear as plain white text. Their styles appear afterward.

## Evidence

Pending submissions use a separate transcript row with a plain paragraph. Accepted messages use `ChatMessage`, which supplies author color, badges, and message layout.
The pending row does not render a display name. It therefore does not fully explain the reported white display name.
The reported visual delay has not been reproduced. Inspect both submission transitions and style availability before selecting a fix.

## Desired behavior

The display name and message have their final styles from their first visible render. Sending and delivery state remain explicit.
The browser is not yet specified. Start reproduction in the project's browser test environment.

## Proposed acceptance criteria

- Reproduce the change with a delayed message response or live-delivery event.
- Capture the first visible display name and message. Neither flashes as unstyled white text before receiving its final style.
- Preserve message typography and spacing from the first visible submission through confirmation.
- Show sending, failure, and retry state without claiming unconfirmed delivery.
- A publication that arrives before the HTTP response produces one message.
- A failed submission remains retryable without losing its text.

## Agent Brief

**Category:** bug

**Summary:** Keep Chat message content visually consistent from pending submission
through acceptance, and apply final author styling on the author's first render.

**Current behavior:**
Pending submissions use plain paragraphs with inherited typography and color.
Acceptance replaces them with smaller, differently colored message content and
adds the styled author. Pending whitespace handling also differs. The content
transition was reproduced; a white author-name flash was not.

**Desired behavior:**
Visible submitted content uses the accepted message's typography, color,
whitespace handling, and content spacing from its first render, including failed
and retried submissions. Any displayed author uses the final author styling on
its first render. Sending, failure, and delayed delivery remain explicit and
accessible. Unconfirmed content must not appear to be confirmed.
Do not invent author tags, badges, server timestamps, or message identifiers to
make pending content look accepted. Author metadata may appear when available;
its absence before acceptance is not itself the reproduced bug.

**Key interfaces:**
- `ChatSubmission` and `useChatSending`: retain submission identity, text,
  retry behavior, and the distinction between pending and accepted content.
- `ChatTranscript` and `ChatMessage`: align pending and accepted content
  presentation without introducing a second independent set of message styles.
- `PublicChatMessage`: retain server-authoritative author metadata and message
  identity. Preserve privacy rules for Chat author tags.

**Acceptance criteria:**
- [x] With an outgoing request held in Chromium, pending text has the same
  computed font size, line height, color, whitespace handling, and content
  spacing as accepted text. Include wrapped text and repeated spaces.
- [x] Capture pending and accepted states. Confirm that content does not flash
  as larger white text and that the first visible author has its final styling.
- [x] Sending remains visible while the request is pending. Preserve existing
  delayed-delivery feedback after acceptance.
- [x] Failed submissions keep their text and provide a working Retry control.
  Retrying keeps the submission identity and consistent content styling.
- [x] A live publication arriving before the HTTP response leaves one message,
  with no stale Sending or Retry state after confirmation.
- [x] Successful sends preserve existing draft clearing and composer focus
  behavior. Confirm rendering at desktop and mobile widths.

**Out of scope:**
- Changing the author color palette or color distribution, which belongs to
  issue 06.
- Adding text size preferences, which belongs to issue 07.
- Redesigning accepted message layout or changing delivery, moderation,
  retention, or privacy rules.
- Speculative changes to stylesheet loading without separate reproduction.
